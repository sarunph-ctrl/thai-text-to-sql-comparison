> **Legacy baseline:** กฎชุดนี้ใช้กับเดโม 5 ตารางเดิมเท่านั้น ถูกแทนที่ในระดับขอบเขตโดย `SCOPE_WMS_MVP.md` และจะไม่ใช้เป็น Ground Truth ของ WMS MVP

**Version:** 0.1-draft

**Updated:** 2026-11-12

**Review status:** Superseded as current scope; retained for legacy demo reproducibility

เอกสารนี้ตรึงความหมายของคำถามและผลลัพธ์ก่อนพัฒนา Rule-based หรือ Prompt รอบถัดไป เพื่อให้ Rule-based, LLM และ SQL อ้างอิงถูกประเมินภายใต้กฎเดียวกัน

## กฎยอดขาย

### SALES-01 — นิยามยอดขาย

ยอดขายคำนวณจาก:

```text
SUM(order_items.qty × order_items.unit_price)
```

และนับเฉพาะรายการที่ `orders.status = 'paid'`

สถานะ `pending` และ `cancelled` ไม่รวมในยอดขาย แม้จะมีรายการสินค้าอยู่ใน Order

### SALES-02 — ช่วงเวลาของยอดขาย

ใช้ `orders.order_date` เป็นฐานเวลา เดือนหนึ่งใช้ช่วง:

```text
order_date >= วันแรกของเดือน
AND order_date < วันแรกของเดือนถัดไป
```

ตัวอย่างเดือนกันยายน 2026 คือ `[2026-09-01, 2026-10-01)` จึงรวมวันที่ 30 กันยายน แต่ไม่รวม 1 ตุลาคม

### SALES-03 — ราคาย้อนหลัง

ใช้ `order_items.unit_price` ซึ่งเป็นราคาขณะขาย ห้ามใช้ `products.price` ซึ่งเป็นราคาปัจจุบัน

### SALES-04 — ยอดขายแยกสินค้า

Group ด้วย `products.id` และชื่อสินค้า ผลลัพธ์แสดงเฉพาะสินค้าที่มียอดขายสถานะ `paid` ในช่วงที่ถาม

### SALES-05 — Top-N สินค้า

“สินค้าขายดี” ในขอบเขตนี้หมายถึงยอดขายเป็นเงิน ไม่ใช่จำนวนชิ้น เรียงตามยอดเงินจากมากไปน้อย และถ้ายอดเท่ากันให้เรียง `products.id` จากน้อยไปมากก่อนเลือก N อันดับ

## กฎสินค้าคงเหลือ

### INV-01 — นิยามยอดคงเหลือ

ยอดคงเหลือต่อสินค้าและคลังคำนวณจากทุก movement ที่บันทึก:

```text
SUM(opening) + SUM(receipt) - SUM(issue)
```

ค่า `qty` ในตารางเป็นจำนวนบวกเสมอ เครื่องหมายบวกหรือลบเกิดจาก `movement_type`

### INV-02 — ระดับการแสดงผล

แสดงหนึ่งแถวต่อคู่สินค้า–คลัง และแสดง `0` สำหรับคู่ที่ไม่มี movement โดยสร้างกรอบจากทุกสินค้า × ทุกคลัง ก่อนเชื่อมยอด movement

### INV-03 — ไม่ใช้สถานะ Order

ยอดคงเหลือไม่กรอง `orders.status` เพราะ movement เป็นเหตุการณ์ทางกายภาพที่แยกจากสถานะการขาย

### INV-04 — ไม่ใช่ยอดย้อนหลัง

คำถามที่รองรับคือยอดจาก movement ทั้งหมดที่บันทึก ณ snapshot ปัจจุบันของฐานข้อมูล ไม่รองรับ “คงเหลือ ณ วันที่...”

## กฎยอดจ่ายออก

### OUT-01 — นิยามยอดจ่ายออก

ยอดจ่ายออกคำนวณจาก `SUM(stock_movements.qty)` เฉพาะ `movement_type = 'issue'`

### OUT-02 — ช่วงเวลา

ใช้ `stock_movements.movement_date` และช่วงเดือนแบบครึ่งเปิดเหมือน SALES-02

### OUT-03 — ระดับการแสดงผล

รวมทุกคลังและแยกตามสินค้า สินค้าที่ไม่มี `issue` ในเดือนนั้นต้องแสดงค่า `0`

### OUT-04 — ความสัมพันธ์กับการขาย

รวม `issue` ทั้งที่เชื่อมและไม่เชื่อม `order_items` และไม่กรอง `orders.status` ดังนั้นยอดจ่ายออกไม่จำเป็นต้องเท่ากับจำนวนสินค้าที่อยู่ในยอดขาย

ตัวอย่าง: Order ที่ยัง `pending` อาจถูกจ่ายออกบางส่วน และ movement เพื่อใช้งานภายในอาจไม่มี Order เลย ทั้งสองกรณียังนับในยอดจ่ายออก

## กฎขอบเขตคำถาม

### SCOPE-01 — Query families ที่รองรับ

1. ยอดขายรวมรายเดือน
2. ยอดขายรายเดือนแยกสินค้า
3. Top-N สินค้าตามยอดขายเป็นเงิน
4. สินค้าคงเหลือแยกสินค้าและคลังจาก movement ทั้งหมด
5. ยอดจ่ายออกรายเดือนแยกสินค้าและรวมทุกคลัง

### SCOPE-02 — เวลาในคำถาม

คำถามรายเดือนต้องระบุชื่อเดือนและปีสี่หลัก รองรับทั้ง พ.ศ. และ ค.ศ. ระบบแปลง พ.ศ. เป็น ค.ศ. ก่อนสร้างช่วงวันที่

### SCOPE-03 — หนึ่งคำถามต่อครั้ง

ไม่มี Conversation memory และไม่ตีความคำอ้างย้อนกลับ เช่น “แล้วเดือนถัดไปล่ะ”

### SCOPE-04 — Read-only

ระบบสร้างและรันเฉพาะ `SELECT` ไม่รองรับคำสั่งเปลี่ยนข้อมูลหรือโครงสร้างฐานข้อมูล

### SCOPE-05 — เงื่อนไขที่ไม่รองรับ

ถ้าคำถามมีเงื่อนไขนอกขอบเขต เช่น ระบุชื่อสินค้า/คลัง ขอราคาปัจจุบัน ขอเปรียบเทียบหลายเดือน หรือถามสต็อกย้อนหลัง ระบบควรปฏิเสธพร้อมเหตุผล ไม่ควรตัดเงื่อนไขทิ้งแล้วรันคำถามที่ความหมายเปลี่ยนไป

## ตารางเชื่อมกฎกับ Query Family

| Query family | กฎหลัก | ตารางและคอลัมน์สำคัญ |
|---|---|---|
| ยอดขายรวมรายเดือน | SALES-01, 02, 03 | `orders.status`, `orders.order_date`, `order_items.qty`, `order_items.unit_price` |
| ยอดขายแยกสินค้า | SALES-01–04 | เพิ่ม `products.id`, `products.name` |
| Top-N | SALES-01–05 | เพิ่มการเรียงยอดเงินและ Tie-break |
| คงเหลือแยกคลัง | INV-01–04 | `stock_movements.movement_type`, `qty`, `product_id`, `warehouse_id` |
| จ่ายออกรายเดือน | OUT-01–04 | `movement_type`, `movement_date`, `qty`, `product_id` |

## ตัวอย่างที่ใช้ยืนยันกฎ

จาก Seed ปัจจุบัน ยอดขายเดือนกันยายน 2026 ที่สถานะ `paid` คือ:

```text
220 + 200 + 200 + 250 + 260 + 120 = 1,250 บาท
```

ต้องไม่รวม:

- Order `cancelled` เดือนกันยายน 1,850 บาท
- Order `pending` เดือนกันยายน 600 บาท
- Order `paid` วันที่ 31 สิงหาคม 100 บาท
- Order `paid` วันที่ 1 ตุลาคม 50 บาท

ตัวอย่างนี้ใช้ตรวจ SALES-01 ถึง SALES-03 และ Boundary ของ SALES-02 ไม่ใช่หลักฐานว่าระบบถูกต้องกับคำถามทุกแบบ

## Protocol สำหรับ Ground Truth

ทุกข้อประเมินต้องเก็บอย่างน้อย:

- `question_id` และข้อความคำถาม
- Query family และ In-scope/Out-of-scope label
- รหัส Business rules ที่ใช้
- Reference SQL ที่ผู้ตรวจอ่านได้
- Expected column names
- Expected rows และชนิดข้อมูล
- ระบุว่าลำดับแถวมีความหมายหรือไม่
- Data snapshot/version ที่ใช้

การตัดสินความถูกต้องหลักให้เปรียบเทียบผลลัพธ์กับ Reference SQL บน snapshot เดียวกัน ไม่บังคับให้ SQL ที่ระบบสร้างมีข้อความเหมือนเฉลย เพราะ SQL ต่างรูปสามารถให้ผลถูกต้องเหมือนกันได้

## Change Control

- ห้ามแก้กฎจากผลของ Held-out test แล้วรายงานผลเดิมต่อ
- ถ้าเปลี่ยนนิยาม, Schema, Seed หรือ Reference SQL ต้องเพิ่ม Version และรันการประเมินใหม่
- Development set ใช้ปรับ Rule-based และ Prompt ได้
- Held-out test set ต้องไม่ใช้ตัดสินใจปรับระบบก่อนการประเมินรอบสุดท้าย
- ผลเดิม 10 ข้อเป็น Preliminary synthetic evaluation ไม่ใช่ข้อสรุปของโครงการ

## ประเด็นที่ต้องให้ผู้ตรวจยืนยัน

- คำว่า “ยอดขาย” ควรยึด `paid` ตามนิยามนี้หรือไม่
- “ขายดีที่สุด” ควรหมายถึงยอดเงินตามวัตถุประสงค์งานหรือไม่
- การแสดงสินค้าที่ไม่มี movement เป็น 0 เหมาะกับทุก Query family หรือเฉพาะ Inventory/Outbound
- Tie-break ด้วย `products.id` เป็นกติกาที่อธิบายและทำซ้ำได้หรือไม่
- ขอบเขต 5 Query families ตรงกับวัตถุประสงค์ในรายงานหรือไม่
